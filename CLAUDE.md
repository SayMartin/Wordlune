# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This repo (internally still named `WordluneNative`, branded to users as just "Wordlune" — renamed from "Wordse" in August 2026 after discovering an unrelated, actively-maintained "Wordse" word-puzzle app already on Google Play with the same exact name and near-identical concept) is an Expo/React Native port of the original Vite-based "Wordse" web app (a Wordle-style word-guessing game), with Supabase as the backend for auth, word data, scores, and realtime multiplayer (Duel mode). When behavior is ambiguous, the original web app's `src/router.jsx` and equivalent hooks are the reference implementation this port mirrors — see comments in `src/navigation/RootNavigator.tsx` for specifics on what's intentionally different. That original web app's repo is being retired in favor of this one; `supabase-ops/` (migrations + seed/content scripts, copied from that repo) is the only remaining home for that project's DB migration history and content-seeding tooling — see `supabase-ops/README.md`. App identifiers: bundle id / Android package `se.wordlune.app`, display name "Wordlune". Some comments throughout the codebase still say "Wordse" when referring specifically to the original ported-from web app (a historical fact, not this app's current name) — that's intentional, not leftover drift.

## Commands

```sh
npm start           # Start Metro/Expo dev server
npm run android      # expo run:android
npm run ios          # expo run:ios (run `bundle install` then `bundle exec pod install` first if native deps changed)
npm run web          # expo start --web (dev server + browser tab)
npm run build:web    # expo export --platform web -> static site in dist/, deployable to any static host
npm run lint          # eslint .
npm test             # jest (jest-expo preset)
```

Run a single test file: `npx jest __tests__/App.test.tsx`.

Requires Node >= 22.11.0. Supabase credentials are read from `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` (`.env`, see `.env.example`). If unset, `src/supabaseClient.ts` falls back to a no-op stub client so the app still renders in dev/test without a backend.

**Never read `.env` files** (repo root, `supabase-ops/`, or anywhere else in this project) — not via `Read`, `grep`, `cat`, or any other tool, even when it seems harmless (e.g. just to find a project URL for a setup instruction). These hold live credentials, including the Supabase service-role key in `supabase-ops/.env` for the seed-upload script, which bypasses RLS. If a value from `.env` is needed, ask the user to paste it, or point them at `.env.example` (key names only, no secrets) instead.

Android builds (`npm run android` / Gradle) need the daemon JVM on **Java 17 or 21**, not whatever the system default happens to be — JDK 24+ trips a JNI-restriction warning during the prefab/CMake native-build steps (`configureCMakeDebug[armeabi-v7a]`) that Android Gradle Plugin misreports as a build failure. Pin it via `org.gradle.java.home` in `~/.gradle/gradle.properties` (machine-local, not the repo's `android/gradle.properties`) rather than changing the system JDK.

**Web target** (`react-native-web`, configured via `web.bundler: "metro"` in `app.config.js`): renders as a full desktop-responsive site (not a phone-frame mockup), matching the original Wordse web app's layout — see `WebTopNav`/`MainTabs` below. `react-native-screens`, `react-native-svg`, `react-native-safe-area-context`, and the Supabase JS client all work through their web-compatible paths. `react` and `react-dom` must stay on the exact same version (a mismatch produces a blank page with a minified React error #527 in the console, no other symptom) — `react-dom` is not in Expo's SDK-managed version set, so bumping `react` requires manually bumping `react-dom` to match. Computer-keyboard input (letters/Enter/Backspace/Space/hyphen) is wired up in `GameScreen.tsx` via a `window.addEventListener("keydown", ...)` effect gated on `Platform.OS === "web"`, mirroring the web app's `Game.tsx` `onKey` handler — native has no equivalent since `addLetter`/`deleteLetter`/`submitGuess` are already reachable via the on-screen `Keyboard` component there.

**Web deployment**: live at `https://wordlune.appfinningar.se`, self-hosted on `smurfserver` (home server), mirroring the `cv-forge` project's pipeline but without any of its backend pieces (no Postgres, no self-hosted-runner migration step — this is a pure static export with no server-side runtime). `Dockerfile` is a multi-stage build: Node 22 runs `npm run build:web` (needs `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_ANON_KEY` as build args, not runtime env vars, since Metro inlines `EXPO_PUBLIC_*` vars into the JS bundle at build time), then `nginx:alpine` serves the resulting `dist/`. `nginx.conf` has a `try_files ... /index.html` SPA fallback — required because `app.config.js` sets `web.output: "single"` and every route (`/game`, `/settings`, `/login`, `/reset-password`, `/privacy`, `/delete-account`, etc.) is handled client-side by React Navigation's `linking` config, so without it a direct link or page refresh on any non-root path 404s instead of loading the app. Security headers live in a separate `security-headers.conf` that each `location` block `include`s — **not** because of redundancy but because nginx drops inherited `add_header` directives in any location declaring its own, and two of the three locations set `Cache-Control`; a server-level block would silently vanish for exactly the JS bundle and `index.html`. It's copied to `/etc/nginx/` rather than `/etc/nginx/conf.d/`, since everything in `conf.d/*.conf` is auto-included at http level. The CSP is calibrated against the real export: `script-src 'self'` is safe (the export has no inline `<script>`), but `style-src 'unsafe-inline'` is unavoidable (inline `<style id="expo-reset">` plus react-native-web's runtime style injection, and a static export has no nonce mechanism). HSTS belongs at Cloudflare, not here — nginx only ever sees plain HTTP behind the tunnel. `.github/workflows/deploy.yml` builds and pushes `ghcr.io/saymartin/wordlune:latest` on every push to `main` (needs those same two vars as repo Actions secrets); `~/wordlune/docker-compose.yml` on smurfserver runs it labeled `com.centurylinklabs.watchtower.enable=true` — no separate Watchtower instance needed, the existing cv-forge one already polls the whole Docker host. Cloudflare Tunnel routes `wordlune.appfinningar.se` to the server's LAN IP (`http://192.168.50.131:3006`) — `http://localhost:3006` doesn't work there since `cloudflared` resolves "localhost" against its own container, not the host.

## Architecture

**Provider stack** (`App.tsx`): `SafeAreaProvider` > `ThemeProvider` > `LoadingProvider` > `AuthProvider` > `NavigationContainer` > `RootNavigator`. Theme colors feed directly into `NavigationContainer`'s theme. No phone-frame wrapper — web renders full-bleed/responsive (see `MainTabs`/`WebTopNav` below).

**Navigation**: `RootNavigator` (native-stack, headers hidden) hosts `MainTabs` (bottom-tabs: Home/Game/Progress/Settings/About) as the `Main` route, plus full-screen stack routes for `Login`/`Signup`/`Signout`/`NotFound`. Real Duel mode lives inside `GameScreen`, not as a separate route (there is no standalone Multiplayer route — that old prototype was removed). Game/Progress/Settings are gated behind `SessionGate` (`src/components/SessionGate.tsx`, wired up in `MainTabs.tsx`), mirroring the web app's `SessionRequiredRoute`: visitors get an inline "Play as Guest / Log In / Sign Up" card instead of the screen; Home/About stay open to visitors. `NotFoundScreen.tsx` mirrors the old web app's `src/pages/NotFound.tsx`; it's reachable on web via the `linking` config passed to `NavigationContainer` in `App.tsx`, which maps `"*"` to `NotFound` (mirroring react-router's catch-all) — every other named route is also given an explicit path there (`game`, `about`, etc.) matching the old app's URLs, since a partial/missing `linking` config would otherwise leave unmatched URLs silently falling through to Home instead of showing the 404. Unlike the old web app there's no separate `/profile` route anymore — `SettingsScreen.tsx` (rendering the `Settings.tsx` component, formerly `ProfileScreen.tsx`/`MyProfile.tsx`) is reachable only via the `Settings` tab at `/settings`; a redundant standalone `Settings` stack route that duplicated the same screen (a dead web-router-compatibility leftover) was removed. `LoginScreen.tsx` (formerly `SigninScreen.tsx`) is registered under the `Login` route name (`/login`).

**Web layout** (`MainTabs.tsx`): on web, `Tab.Navigator`'s bottom tab bar is replaced with `WebTopNav.tsx` via the `tabBar` prop plus `tabBarPosition: "top"` in `screenOptions` (bottom-tabs renders whatever `tabBar` returns at the position given by `tabBarPosition` — without it, a custom `tabBar` still renders at the *bottom*). `WebTopNav` mirrors the original site's `HeaderCopy.tsx`: full-width bar containing a `max-w-4xl`-equivalent (896px, `WebCentered.tsx`) centered row — logo (`Logo.tsx`) + title + language flag, centered Home/Game/Progress/Settings/About links (active link bold+underlined, built dynamically off `state.routes` so tab renames propagate automatically), and a greeting (`AuthStatusIcon.tsx` + name) + Log In/Log Out button. Below `useWindowDimensions()`'s 768px breakpoint it collapses to a hamburger dropdown, same breakpoint as the original's Tailwind `md`. Each tab screen (and Login/Signup/Signout in `RootNavigator.tsx`) is individually wrapped in `WebCentered` rather than capping the whole navigator, since capping `Tab.Navigator` itself would also shrink `WebTopNav`'s full-width bar. `WebFooter.tsx` (web-only) reproduces the original's page footer.

Native's screen content is untouched by any of this — `isWeb` (`Platform.OS === "web"`) gates every branch — but native's per-screen header (`MainTabs.tsx`'s `screenOptions`) deliberately mirrors two of web's choices rather than diverging: `headerLeft: () => <HeaderLeft />` puts the logo + language flag in the same spot as `WebTopNav`'s brand cluster (the flag used to sit on the *right*, next to Log Out, via `HeaderRight.tsx` — moved for cross-platform consistency after it was flagged as confusing), and `headerTitle: () => null` hides the per-screen title text ("Game", "Settings", ...) the same way web's top nav has no "current page" label. `HeaderRight.tsx` keeps native's greeting + Log In/Log Out cluster (bottom tabs still show their own labels/icons as before — only the *header* title is hidden).

**Auth** (`src/context/AuthContext.tsx`): wraps Supabase auth (email/password, anonymous sign-in). Derives `authState` = `"visitor" | "guest" | "registered"` from session presence and `session.user.is_anonymous`. Anonymous ("guest") users get a real Supabase session, just flagged anonymous. `AuthStatusIcon.tsx` (used by both `WebTopNav.tsx` and `HeaderRight.tsx`, next to the greeting text) renders a small looping animation keyed off `authState` instead of a static glyph — 👋 (reuses `WavingHand.tsx`) for `visitor`, a gently nodding 👤 for `guest`, a twinkling ⭐ for `registered` — each its own `Animated.loop`. Both `logout()` and `deleteAccount()` pass `signOut({ scope: "local" })` **explicitly** — supabase-js defaults to `"global"`, which revokes every refresh token the user holds, so a plain "Log Out" in a browser would also sign them out on their phone. Don't drop the argument: the safety case for global is thin here (`clearStoredKeys()` already wipes the session and the in-progress round from the device), and in `deleteAccount()` a global sign-out is a guaranteed-to-fail round-trip since the `auth.users` row is already gone. The global counterpart is `logoutEverywhere()`, surfaced as `SessionsPanel.tsx` in Settings — both go through one `performSignOut(scope, timeoutMs)` helper. The timeout differs on purpose: 1s for a plain logout (which must never hang, and where being wrong costs nothing since the device is wiped locally anyway) versus 8s for "everywhere", where the answer decides whether the user can be *told* their other sessions are gone. `SessionsPanel` renders `null` for guests — a guest account has no credentials, so it can never have a second session to revoke. Registered accounts can be signed in on several devices at once; a guest session exists only on the device that created it.

`logout()` races `signOut()` against a 1s timeout and always clears local state/AsyncStorage `sb-*-auth-token` keys regardless of network outcome, so logout can't hang — the initial `checkAuthStatus()` call races `getSession()` against a 5s timeout for the same reason, and its `catch` path always sets `session` to `null` too, since `SessionGate.tsx` treats `session === undefined` as "still loading" and would otherwise spin forever for a logged-out visitor if `getSession()` hung or threw before `session` was ever set.

Profile rows (`player_profiles`) are fetched via `fetchOrCreateProfile()` in `AuthContext.tsx`: `getPlayerProfile()` (`src/supabase/players-repository.ts`) retries a few times on Postgres `PGRST116` ("no rows") to ride out the `on_auth_user_created` DB trigger's insert — a common race right after signup/anonymous sign-in — and if the row is still missing after that, `ensurePlayerProfile()` creates it client-side instead of leaving the session permanently profile-less (this also self-heals older sessions whose trigger insert failed outright, e.g. a guest created before `display_name` was NOT NULL-enforced). A separate `profileLoading` boolean (distinct from `loadingInitial`) lets consumers like `Settings.tsx` distinguish "still fetching the profile" from "fetched and it's genuinely missing/errored," so they show a retry affordance instead of an infinite spinner.

`signUpNewUser()` branches on `session.user.is_anonymous`: a signed-in guest is **upgraded in place** via `updateUser({ email, password })`, which keeps the same `auth.users.id` so every FK (`player_profiles`, `game_scores`, `duel_matches`) follows automatically. Calling `signUp()` for a guest instead would mint a *new* id and strand their scores on an orphaned account. Two things the upgrade path must do that a fresh signup gets for free: write `player_profiles` explicitly (`handle_new_user()` is an AFTER **INSERT** trigger, so it never fires on an update, and the chosen display name would stay `Guest52`), and treat "your own current display name" as available (`isOwnCurrentName` in `SignupScreen.tsx`, same guard `Settings.tsx` uses). The account stays `is_anonymous` until the confirmation email is clicked, so the result carries `upgraded: true` and the screen says "keep playing" rather than "go to sign in".

`login`/`signUpNewUser`/`loginAnonymously` all return an `errorCode` (Supabase auth-js's `error.code`, e.g. `invalid_credentials`, `email_not_confirmed`) alongside the raw `error` message; screens pass both through `translateAuthError()` (`src/utils/authErrors.ts`) to show a localized message for known codes, falling back to Supabase's (always-English) raw text for anything unmapped. `SignupScreen.tsx` also does its own client-side validation before calling `signUpNewUser` — email required + format-checked, password minimum 8 characters with a required confirm-password field — as a first line of defense ahead of whatever Supabase's own (dashboard-configured, not visible in code) password policy enforces server-side.

Forgot-password is a two-step flow: `requestPasswordReset(email)` (an inline expandable panel on `LoginScreen.tsx`, not a separate route) calls `supabase.auth.resetPasswordForEmail` with a dedicated `RESET_PASSWORD_REDIRECT_URL` (same web-origin/native-custom-scheme split as `AUTH_REDIRECT_URL`, but pointed at `/reset-password` instead of the app root) so the emailed link lands on `ResetPasswordScreen.tsx`; clicking it authenticates the browser with a recovery session via `detectSessionInUrl` (same mechanism as email confirmation), which is enough for `updatePassword(newPassword)` (`supabase.auth.updateUser`) to succeed without the old password. Like signup's email-confirm redirect, this isn't wired up on native yet (no custom URL scheme handling registered).

Guest accounts are never deleted by the app itself — a "Play as Guest" login creates a permanent `auth.users` row (just flagged `is_anonymous = true`) with an auto-refreshing session, so it persists forever unless something explicitly cleans it up. `supabase-ops/migrations/20260818_cleanup_anonymous_users.sql` (applied, `pg_cron` enabled) schedules a daily job deleting anonymous accounts inactive 14+ days, cascading into `player_profiles`/`game_scores`/`duel_matches` — the latter's FKs had no `ON DELETE` behavior before that migration and would otherwise block deleting a guest who'd played a Duel.

Players (guest or registered) can self-delete their own account from Settings' "Danger Zone" (`Settings.tsx`, confirmed via `ConfirmationOverlay`). A regular client can't delete its own `auth.users` row directly (needs the service-role key), so `deleteAccount()` in `AuthContext.tsx` calls `deleteOwnAccount()` (`src/supabase/players-repository.ts`), which RPCs into `public.delete_own_account()` — a `security definer` Postgres function (`supabase-ops/migrations/20260818_delete_own_account.sql`, same pattern as `cleanup_anonymous_users()`) that deletes `auth.users` for `auth.uid()`. Cascades through the same FKs as the guest cleanup job above; nothing else needs touching since the only other tables that ever referenced `auth.users(id)` directly (`matches`, `boards`) are unused dead code and `player_settings` is dead too (settings actually live in `player_profiles.metadata`, see `updatePlayerSettings()`). After a successful delete, `deleteAccount()` clears local session state the same way `logout()` does.

**Game engine** (`src/hooks/useGame.ts`): owns the core Wordle state machine — persisted to AsyncStorage (`wordlune:game:v1`) for practice mode only; duel/challenge modes always start from an explicit secret and skip persistence/restore. `evaluateGuess` normalizes hyphen/dash variants and whitespace so multi-word or hyphenated secrets (e.g. category words) evaluate sensibly. Mode is one of `"practice" | "competitive" | "duel"`, driven by `gameModeProp` plus `overrideSecret`. `addLetter` also implicitly starts a round (`idle`→`playing`) if a player types before pressing ▶ Play — that transition stamps `startTime` too, not just the explicit `startPlaying()` path, since `PracticeResultOverlay`'s elapsed-time display (`durationSeconds`) needs both `startTime` and `endTime` set and silently falls back to showing 0 otherwise.

Composed hooks layered on top of `useGame`, all driven from `GameScreen`:
- `useWordPool` — fetches/filters the candidate word list from Supabase (`words-repository.ts`) based on mode/category/subcategory/length filters; also picks the initial secret for practice mode. Duel mode always pulls from a fixed "Hydrocarbons" subcategory of 5-letter words (`listHydrocarbonFiveLetterWords`).
- `useDuelMode` — realtime 1v1 duel logic over a Supabase Realtime channel (`game:<matchId>`), broadcasting `guess`/`duel_status`/`game_control` events and using presence sync to detect opponent disconnects (auto-awards victory if the opponent leaves mid-duel). Scoring: 5 pts per correct letter, 2 pts per present letter, summed client-side per player and reconciled via broadcast. The hook owns `suddenDeathEndTime`/`setSuddenDeathEndTime` and the auto-forfeit timer off it, but never *sets* it itself — `GameScreen.tsx` must call `setSuddenDeathEndTime(Date.now() + 60000)` when `opponentLost` fires (mirroring the web app's `Game.tsx`), or the whole mechanic silently never triggers despite the hook's internals working fine.
- `useChallengeMode` — multi-word "challenge" runs backed by `challenge_attempts`/`challenge_results` tables; tracks progress index across a fixed word list and only persists a summary row at the end (per-word scores aren't saved individually in competitive/challenge mode).

**Supabase layer** (`src/supabase/*-repository.ts`): thin query wrappers, no ORM. Key tables: `player_profiles`, `game_scores`, `challenge_attempts`/`challenge_results`/`competitive_challenges`, `duel_matches`, `words`/`categories`/`subcategories`/`words_subcategories`. Words are stored with per-language columns (`word_en`, `word_se`/`word_sv` — note the inconsistent `se`/`sv` suffix across tables, handled ad hoc per query). Leaderboards read from DB views (`leaderboard_entries`, `duel_leaderboard`, `player_history_view`, `challenge_menu_stats`) rather than raw tables so visibility/aggregation rules live in Postgres, not the client.

**RLS model** (`supabase-ops/migrations/20260821_gdpr_privacy_helpers.sql` + `20260822_gdpr_rls_lockdown.sql`): every personal-data table is **own-row-only** (`auth.uid() = player_id`). Before those migrations, `player_profiles`, `game_scores`, `challenge_results` and `duel_matches` all carried `SELECT USING (true)`, meaning the whole tables were readable with the anon key that ships in the web bundle — the `is_public` opt-in existed only in the views, never in RLS, so it protected nothing against a direct PostgREST query. Anything that legitimately needs to show *other* players now goes through an owner-rights view or a `security definer` RPC that applies its own gate: `display_name_available()`/`suggest_display_name()` (signup name checks), `duel_lobby` (open invitations — deliberately omits `secret_word`, which non-participants could previously read straight off `duel_matches`), `match_player_names()` (participants only), and the three leaderboard views (each gated on `is_public`). `player_history_view` is `security_invoker = true` *and* filters on `auth.uid()`; the leaderboard views are pinned `security_invoker = false` explicitly so a future default change can't silently empty or expose them. When adding a query that reads another player's row, add a gated RPC/view — don't loosen the table policy.

The old generic `board_events`/`board_state` pub/sub layer (`src/shared/useBoardRealtime.ts` plus four helpers in `words-repository.ts`) was **removed** — it had zero consumers anywhere in `src/`, and its `user_id` column was personal data that no deletion path could reach. `matches`, `boards` and `player_settings` were dropped in the same migration for the same reason. Duel realtime is unaffected: it lives in `useDuelMode`'s own channel.

**i18n** (`src/i18n/i18n.ts`): `en`/`sv`/`fr` resources from `src/locales/*/translation.json` — all three files must share the exact same key set (verify with a `t("...")` grep-vs-JSON-diff sweep across `src/`; the project has been bitten before by locale drift). Language is never auto-detected from device locale — it defaults to English and only restores a previously *user-selected* language cached in AsyncStorage (`wordlune:lang`), mirroring the web app's detector config. `WebTopNav.tsx`/`HeaderLeft.tsx` (native) expose language switching as a single flag icon next to the logo that *cycles* en→sv→fr→en (`src/utils/languageCycle.ts`'s `LANGUAGE_CYCLE`/`flagFor`/`nextLanguage`) rather than a dropdown — deliberately minimal for 3 languages, revisit if a 4th is added. French is **accent-sensitive** by design (like Swedish ÅÄÖ, unlike some other language Wordle clones) — "cafe" does not match secret "café"; this needed no comparison-logic changes since `evaluateGuess`/`normalizeForCompare` (`src/hooks/useGame.ts`, `src/utils/wordUtils.ts`) already did plain exact-character matching.

The on-screen keyboard (`Keyboard.tsx`'s `LAYOUTS`) uses real AZERTY rows for French (`AZERTYUIOP`/`QSDFGHJKLM`/`WXCVBNÄÖÅ`) plus a 4th row of the 10 real French accented letters (`ÉÈÊÀÂÇÎÔÙÛ`); the physical-keyboard handler in `GameScreen.tsx` (`LETTER_PATTERNS.fr`) accepts the same set plus Å (Å isn't native French but is needed for the Swedish-place-name loanwords below — easy to forget since it's not visually grouped with Ä/Ö). Ä/Ö/Å (also not native French) are tacked onto the end of the `WXCVBN` row rather than the already-full accent row. Delete (`⌫`) lives on the Enter row for *every* language now — to the right of Enter, in a `flex`-shared zone with whatever else is on that side — rather than at the end of the last letter row, so it has one consistent, predictable spot regardless of how many letter rows a language has. French additionally moves space/hyphen to the Enter row's *left* zone (`SPACE_HYPHEN_ON_ENTER_ROW`), since its accent row has no room left for them. The Enter key itself is a fixed 50%-width, always-centered `Pressable` flanked by two equal-`flex` zones (so it stays centered whether one zone is empty or both hold keys) — its side-key children (`sideKey` style) are deliberately never combined with the letter-key style (`key`) in one `style={[...]}` array, since react-native-web can flatten conflicting `flex`/`width` values from merged style objects unpredictably and collapse a button to near-zero width.

Word/category/subcategory content is per-language via `word_en`/`word_sv`/`word_fr` and `name_en`/`name_sv`/`name_fr` columns (`words`/`categories`/`subcategories` tables) — `src/supabase/langColumns.ts`'s `wordColumn()`/`nameColumn()` resolve a language code to the right column name (also fixed a latent bug where some queries used a nonexistent `word_se` column instead of `word_sv`). `supabase-ops/migrations/20260818_add_french_language.sql` added the `_fr` columns and populated them for every existing word/category/subcategory — brand-name categories (car/bicycle/motorcycle) got `word_fr = word_en` (untranslatable proper nouns), Swedish place-name categories got `word_fr = word_sv` (keeps correct native diacritics), everything else (countries/capitals/hydrocarbons common nouns/ship types) got real French translations. The seed CSVs (`supabase-ops/migrations/seeds/**/*.csv`) mirror the same translations in new `_fr` columns for future-reseeding value, though the live DB was populated directly by the migration, not by re-running the seed pipeline. `supabase-ops/scripts/generate_challenge.mjs` requires a word to exist in all three languages (not just en/sv) before selecting it for a daily challenge.

`word_en` must always be ASCII-transliterated, even for categories whose `word_fr` deliberately keeps native diacritics (the Swedish place-name categories above) — English's on-screen keyboard has no Å/Ä/Ö keys and `LETTER_PATTERNS.en` only matches `[A-Za-z]`, so a non-transliterated `word_en` (e.g. `Färjestaden` instead of `Farjestaden`) makes that round unsolvable for an English-language player. `supabase-ops/migrations/20260820_fix_english_diacritics_oland_skanor.sql` fixed the 31 rows that had been missed this way (all of "Villages on Öland" in `villages-öland.csv`, plus one stray row in `cities-sweden.csv`) — not yet applied against the shared project as of 2026-08-20, and scoped to just those two files, not a full audit of every category/language (see the migration's own comment and `supabase-ops/README.md`).

**Google Play**: not published, and deliberately not started — see `GOOGLE-PLAY.md` for the full pre-publication checklist (what's already done, the release-signing blocker, the Data safety answers, and the 12-testers-for-14-days timeline trap on personal developer accounts). Android-side GDPR/permission work is already landed; don't redo it.

**GDPR surfaces**: `PrivacyPolicyScreen.tsx` (`/privacy`) and `DeleteAccountScreen.tsx` (`/delete-account`) are root-stack routes, both deliberately **outside** `SessionGate` — a visitor must be able to read the policy before signing up, and both URLs are registered with Google Play (Play requires a *web* URL for account deletion even though the app offers it in-app). `DeleteAccountPanel.tsx` is the single implementation of the delete flow, rendered by both that screen and Settings' Danger Zone. Policy text lives in ~78 flat `privacy_policy_*` / `delete_account_*` i18n keys at paragraph granularity (not one key per section — that makes translation review impossible), and `PRIVACY_POLICY_VERSION` in `src/constants/privacy.ts` doubles as the policy's "last updated" date so the stamped version and the displayed date can't drift. Note `privacy_status` is an *old* key meaning leaderboard visibility, not a GDPR statement — its display text was renamed accordingly.

**Avatars** (`src/components/Avatar.tsx`): generated locally with `react-native-svg`, deterministically from a seed — never fetched. `avatar_url` holds a `wordlune:avatar:<seed>` token (`localAvatarUrl()`), and a **null** `avatar_url` is normal: `Avatar` then derives the seed from the display name. This replaced `api.dicebear.com` URLs, which sent another player's display name *and the viewer's* IP/User-Agent to a third party on every profile, leaderboard and duel-card render, for a decorative image. `Avatar` still renders a leftover `http(s)` URL as a remote `Image` so native clients on an older bundle don't break; that branch can go once they can't write one (`20260823_drop_dicebear_avatars.sql` nulls the existing rows). Don't reintroduce a remote avatar service without adding it to the CSP, the policy's recipient list, and the Play Data safety declaration.

**Data export** (`exportMyData()` in `players-repository.ts` + `src/utils/exportDownload.ts`): the Art. 15/20 request, self-served from Settings → Data & Privacy. Six parallel own-row queries plus the `wordlune:*` device keys, delivered as JSON. Web and native need genuinely different delivery — react-native-web's `Share.share()` delegates to `navigator.share` and *rejects* when unavailable, so the Blob/`<a download>` path is required, not a nicety; native writes to `Paths.cache` and opens the share sheet via `expo-sharing`. The session token is deliberately excluded from the export: it's a live credential, not user data.

**Local storage** (`src/utils/localStorageKeys.ts`): every `wordlune:*` AsyncStorage key is declared here rather than as a module-local const in its consumer, so `clearStoredKeys()` can wipe them on logout/deletion without a second hardcoded copy of each string. Scope differs per path on purpose: **logout** clears the Supabase session + `wordlune:game:v1` (it holds the secret word, which matters on a shared computer) but keeps theme/language/reduceMotion as device preferences; **account deletion** clears all of it.

**Theming** (`src/theme/ThemeProvider.tsx`): simple light/dark palette context (not system-linked), always initializes to `"dark"` on boot regardless of persisted value, matching the web app's behavior. Screens consume `colors` from `useTheme()` and apply them manually in `StyleSheet` — there's no CSS-class-based theming.

**Board tiles on web** (`src/components/BoardGrid.tsx`): tile size is fixed per word length on native (phone-tuned table), but on web it grows to fill available space via `useWindowDimensions()` — bounded by both a width fit (against the 896px `WebCentered` column) and a height budget (`windowHeight * 0.32`, since the board sits in a `ScrollView` alongside the header/controls/keyboard/footer). The overall cap is deliberately modest (38px, not width-fit's actual max) — raising it reintroduces vertical scrolling on shorter desktop viewports because the height budget was tuned against that cap, not derived independently. `Keyboard.tsx` intentionally keeps its original fixed key size on web (not scaled to match) per explicit user preference.

**Mode toggle / header-row pills** (`src/components/GameModeToggle.tsx`, sitting in `CategorySelector`'s `headerRow`): both the Practice/Competitive/Duel toggle buttons and `CategorySelector`'s "Select Categories" expand button use an explicit fixed `height: 40` (not padding-derived height) so they line up pixel-for-pixel on the shared row — emoji glyphs (☕🏆⚔️) render with inconsistent line-box metrics across browsers/fonts, so matching heights via padding+line-height alone doesn't reliably hold across environments. `GameModeToggle` renders all three modes as icon-only 40×40 squares — no text label even for the active mode; the active one is signaled by a `colors.accent` fill instead, and `accessibilityLabel` carries the full name for screen readers. On web, `onHoverIn`/`onHoverOut` show a small custom tooltip bubble with the mode name — react-native-web doesn't forward a `title` prop through `Pressable` to the DOM, so a native browser tooltip isn't an option here; native has no hover concept so the tooltip simply never renders there (no `Platform.OS` check needed).

**Letter-range filter** (`src/components/LetterSlider.tsx`, used from `GameScreen.tsx`): renders as `[−] min [+] ≤ ABC ≤ [−] max [+] (count)` on one row — `+`/`−` stepper buttons, not the native slider it originally was (`@react-native-community/slider` was removed from `package.json` entirely; `LetterSlider` was its only user). Buttons are visually compact (32px) but use `hitSlop={8}` to still meet Material Design's 48dp minimum touch target without inflating the row's height. The displayed min is `minValue + 1` with `≤` on both sides, even though the underlying filter is exclusive (`word.length > minValue`) — mathematically identical, but "1 ≤" reads better than "0 <" for a count that can never be 0.

`DEFAULT_MAX_LETTERS = 8` (`GameScreen.tsx`) is a genuinely active filter, not a "no filter yet" sentinel like it briefly was mid-refactor — `filterMax` is always `maxLetters`, never `undefined`. It's capped at `ABSOLUTE_MAX_LETTERS = 12`: past that, `BoardGrid.tsx`'s native tile size table shrinks to a near-illegible 14px and — since that row has no horizontal scroll fallback — the board can overflow narrow phone screens outright. `ControlDashboard.tsx`'s Play button is disabled (with a `no_words_for_filter` hint text) whenever the current filter/category selection yields zero words, rather than letting a player start a round they can never win.
