# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Git is the user's, not yours

**Never run a git command that writes — `commit`, `push`, `merge`, `rebase`, `tag`, `reset`, `revert`, `cherry-pick`, `stash`, branch creation or deletion — on your own initiative.** Stage changes if that helps, leave them in the working tree, and say what you changed. Martin does the committing.

Read-only git (`status`, `log`, `diff`, `show`, `branch --show-current`, `ls-tree`) is always fine and needs no permission.

The exception is a genuine necessity — not convenience, not tidiness, not "this feels like the natural next step after the edit". In that case **ask first and wait**, then do only what was agreed. Don't ask routinely: if there is no real reason, there is no question to raise, and a request to change files is not a request to commit them.

Why this matters more here than in most repos: `.github/workflows/deploy.yml` builds and ships the production container image on **every push to `main`**, and Watchtower on the self-hosted server picks it up within about a minute. A push to `main` is a production deploy of a public site, not a bookkeeping step.

## Project

This repo (internally still named `WordluneNative`, branded to users as just "Wordlune" — renamed from "Wordse" in August 2026 after discovering an unrelated, actively-maintained "Wordse" word-puzzle app already on Google Play with the same exact name and near-identical concept) is an Expo/React Native port of the original Vite-based "Wordse" web app (a Wordle-style word-guessing game), with Supabase as the backend for auth, word data, scores, and realtime multiplayer (Duel mode). When behavior is ambiguous, the original web app's `src/router.jsx` and equivalent hooks are the reference implementation this port mirrors — see comments in `src/navigation/RootNavigator.tsx` for specifics on what's intentionally different. That original web app's repo is being retired in favor of this one; `supabase-ops/` (migrations + seed/content scripts, copied from that repo) is the only remaining home for that project's DB migration history and content-seeding tooling — see `supabase-ops/README.md`. App identifiers: bundle id / Android package `se.wordlune.app`, display name "Wordlune". Some comments throughout the codebase still say "Wordse" when referring specifically to the original ported-from web app (a historical fact, not this app's current name) — that's intentional, not leftover drift.

**Positioning: the game tests general knowledge, not vocabulary.** The category is the puzzle — knowing the answer is a five-letter African capital is knowledge doing the work; knowing only that it is five letters is letter frequency and luck, which is the same game whoever plays it. All the outward copy was rewritten to say so (Home hero, About, and `public/index.html`'s `title`/`description`/OG/Twitter tags, which is what Google shows): "expand your vocabulary" and "embark on a linguistic journey" are gone, and nothing should reintroduce them. This is also why hints are always on and why the challenge menu no longer names its theme — see the hint rules further down. The name deliberately did **not** change: `Wordlune` promises nothing about vocabulary, so the copy was the only thing that was wrong.

**If this repo is made public, `CLAUDE.md` goes public with it.** The infrastructure specifics it used to carry — the server's LAN address and port, its hostname, the container image path, the backup bucket name — have been taken out, and new ones must not go back in. Say *what* a thing is and *why* it is that way; the address, the bucket and the port belong in the server's own config, not in a repository. The reasoning is what makes this file useful, and none of it needs an identifier to survive: "the tunnel must target the LAN address, because `cloudflared` resolves localhost against its own container" teaches the same lesson as the IP did. `README.md` is the outward-facing document and is deliberately free of setup instructions, environment variable names and hostnames — written to be read, not to make standing up a copy convenient.

## Commands

```sh
npm start           # Start Metro/Expo dev server
npm run android      # expo run:android
npm run ios          # expo run:ios (run `bundle install` then `bundle exec pod install` first if native deps changed)
npm run web          # expo start --web (dev server + browser tab)
npm run build:web    # expo export --platform web -> static site in dist/, deployable to any static host
npm run lint          # eslint .
npm test             # jest (jest-expo preset)
```

Run a single test file: `npx jest __tests__/App.test.tsx`.

Requires Node >= 22.11.0. Supabase credentials are read from `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` (`.env`, see `.env.example`). If unset, `src/supabaseClient.ts` falls back to a no-op stub client so the app still renders in dev/test without a backend.

**Never read `.env` files** (repo root, `supabase-ops/`, or anywhere else in this project) — not via `Read`, `grep`, `cat`, or any other tool, even when it seems harmless (e.g. just to find a project URL for a setup instruction). These hold live credentials, including the Supabase service-role key in `supabase-ops/.env` for the seed-upload script, which bypasses RLS. If a value from `.env` is needed, ask the user to paste it, or point them at `.env.example` (key names only, no secrets) instead.

Android builds (`npm run android` / Gradle) need the daemon JVM on **Java 17 or 21**, not whatever the system default happens to be — JDK 24+ trips a JNI-restriction warning during the prefab/CMake native-build steps (`configureCMakeDebug[armeabi-v7a]`) that Android Gradle Plugin misreports as a build failure. Pin it via `org.gradle.java.home` in `~/.gradle/gradle.properties` (machine-local, not the repo's `android/gradle.properties`) rather than changing the system JDK.

`typescript` is pinned to **6.x** and must stay below 6.1 — that's `@typescript-eslint`'s peer ceiling (`>=4.8.4 <6.1.0`, still true of the latest 8.x as of 2026-08-21), and nothing in the ESLint ecosystem supports TypeScript 7 yet. The repo shipped `^7.0.2` from its initial commit, which meant `npm run lint` had never once worked: npm resolved the peer conflict by nesting the whole lint toolchain (`@typescript-eslint/*`, `eslint-plugin-jest`, a private `typescript@6`) under `node_modules/@react-native/eslint-config/node_modules/`, where ESLint 8's eslintrc plugin resolution — which looks in the *project root*, not next to the shareable config — couldn't find it. The symptom was an unrelated-looking `Environment key "jest/globals" is unknown` at config-load time. `typescript` is in `expo.install.exclude`, so `npx expo install --fix` won't drag it back to a managed version; if someone bumps it to 7 again, lint breaks the same silent way. `.eslintignore` exists because `dist/` (the minified `build:web` export) otherwise contributes ~27k warnings and buries everything in `src/`.

**Web target** (`react-native-web`, configured via `web.bundler: "metro"` in `app.config.js`): renders as a full desktop-responsive site (not a phone-frame mockup), matching the original Wordse web app's layout — see `WebTopNav`/`MainTabs` below. `react-native-screens`, `react-native-svg`, `react-native-safe-area-context`, and the Supabase JS client all work through their web-compatible paths. `react` and `react-dom` must stay on the exact same version (a mismatch produces a blank page with a minified React error #527 in the console, no other symptom) — `react-dom` is not in Expo's SDK-managed version set, so bumping `react` requires manually bumping `react-dom` to match. Computer-keyboard input (letters/Enter/Backspace/Space/hyphen) is wired up in `GameScreen.tsx` via a `window.addEventListener("keydown", ...)` effect gated on `Platform.OS === "web"`, mirroring the web app's `Game.tsx` `onKey` handler — native has no equivalent since `addLetter`/`deleteLetter`/`submitGuess` are already reachable via the on-screen `Keyboard` component there.

**Web deployment**: live at `https://wordlune.appfinningar.se`, self-hosted on a home server, mirroring the `cv-forge` project's pipeline but without any of its backend pieces (no Postgres, no self-hosted-runner migration step — this is a pure static export with no server-side runtime). `Dockerfile` is a multi-stage build: Node 22 runs `npm run build:web` (needs `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_ANON_KEY` as build args, not runtime env vars, since Metro inlines `EXPO_PUBLIC_*` vars into the JS bundle at build time), then `nginx:alpine` serves the resulting `dist/`. `nginx.conf` serves the SPA shell for client-side routes — required because `app.config.js` sets `web.output: "single"` and every route (`/game`, `/settings`, `/login`, `/reset-password`, `/privacy`, `/delete-account`, etc.) is handled client-side by React Navigation's `linking` config, so without it a direct link or page refresh on any non-root path 404s instead of loading the app. It is deliberately **not** a blanket `try_files ... /index.html`: that answered 200 for every URL ever requested, including typos and `/sitemap.xml`, which is a soft 404 and a low-quality signal to crawlers. Instead a regex `location` lists the known routes (keep it in step with `linking.config.screens` in `App.tsx`) and answers 200, while everything else falls through to `error_page 404 /404.html` — `404.html` is a build-time copy of `index.html` (made in the `Dockerfile`), so the app still boots and renders `NotFoundScreen` while the status line stays honest. A route missing from the regex still renders correctly, it just answers 404. Security headers live in a separate `security-headers.conf` that each `location` block `include`s — **not** because of redundancy but because nginx drops inherited `add_header` directives in any location declaring its own, and two of the three locations set `Cache-Control`; a server-level block would silently vanish for exactly the JS bundle and `index.html`. It's copied to `/etc/nginx/` rather than `/etc/nginx/conf.d/`, since everything in `conf.d/*.conf` is auto-included at http level. The CSP is calibrated against the real export: `script-src 'self'` is safe (the export has no inline `<script>`), but `style-src 'unsafe-inline'` is unavoidable (inline `<style id="expo-reset">` plus react-native-web's runtime style injection, and a static export has no nonce mechanism). HSTS belongs at Cloudflare, not here — nginx only ever sees plain HTTP behind the tunnel. `.github/workflows/deploy.yml` builds and pushes the image to GHCR on every push to `main` (needs those same two vars as repo Actions secrets); a `docker-compose.yml` on the server runs it labeled `com.centurylinklabs.watchtower.enable=true` — no separate Watchtower instance needed, the existing cv-forge one already polls the whole Docker host. Cloudflare Tunnel routes `wordlune.appfinningar.se` to the server's **LAN address**, not to `localhost` — `cloudflared` resolves "localhost" against its own container rather than the host, so a loopback target silently fails to connect. (The actual address and port live in the tunnel config on the server, deliberately not here.)

**`public/`** is the source of the exported `index.html`, not a leftover: Expo uses `public/index.html` as the HTML template for `web.output: "single"` and copies everything else in the directory to `dist/` verbatim (`robots.txt`, `sitemap.xml`, `og-image.png`). Edit the template there — never `dist/`, which is generated and gitignored. Expo injects the favicon `link` and the bundle `script` itself at export time, so the template deliberately omits both. There is no canonical link element: every route is served the same HTML, so one hardcoded canonical would tell Google that `/game`, `/about` and the rest are all really `/` and shouldn't be indexed separately — per-route canonicals would need server-rendered HTML per route, which React Navigation (unlike Expo Router) doesn't produce. Note Cloudflare also injects a *managed* `robots.txt` for this zone; `public/robots.txt` mirrors its AI-crawler blocks so the outcome is the same either way, but only the local one carries the `Sitemap:` line — check which actually wins after a deploy.

**Backups and local dev DB** (`supabase-ops/`): the database is Supabase managed cloud, so there's no container to `docker exec` into the way cv-forge's backup does — `supabase-ops/scripts/backup.sh` runs `pg_dump` in a throwaway `postgres:17-alpine` against the Supabase **session pooler on 5432** (the transaction pooler on 6543 has no prepared statements and fails; the direct `db.<ref>` host is IPv6-only), encrypts with `age` using a **public** key so the server can write backups but never read them, and uploads to the project's R2 backup bucket. It dumps `public` **and `auth`** — without the auth schema every account is gone and every FK dangles. `supabase/config.toml` configures a local `supabase start` stack for rehearsing migrations; it costs no free-tier project slot. `enable_anonymous_sign_ins = true` there is load-bearing — guest mode is a real anonymous session, and the CLI default of `false` makes it fail like an app bug. See `supabase-ops/README.md` for the restore procedure and the baseline-migration approach (the 49 hand-applied migrations are *not* in run order, so they're kept as history rather than replayed).

## Architecture

**Provider stack** (`App.tsx`): `SafeAreaProvider` > `ThemeProvider` > `LoadingProvider` > `AuthProvider` > `NavigationContainer` > `RootNavigator`. Theme colors feed directly into `NavigationContainer`'s theme. No phone-frame wrapper — web renders full-bleed/responsive (see `MainTabs`/`WebTopNav` below).

**Navigation**: `RootNavigator` (native-stack, headers hidden) hosts `MainTabs` (bottom-tabs: Home/Game/Progress/Settings/About) as the `Main` route, plus full-screen stack routes for `Login`/`Signup`/`Signout`/`NotFound`. Real Duel mode lives inside `GameScreen`, not as a separate route (there is no standalone Multiplayer route — that old prototype was removed). Game/Progress/Settings are gated behind `SessionGate` (`src/components/SessionGate.tsx`, wired up in `MainTabs.tsx`), mirroring the web app's `SessionRequiredRoute`: visitors get an inline "Play as Guest / Log In / Sign Up" card instead of the screen; Home/About stay open to visitors. `NotFoundScreen.tsx` mirrors the old web app's `src/pages/NotFound.tsx`; it's reachable on web via the `linking` config passed to `NavigationContainer` in `App.tsx`, which maps `"*"` to `NotFound` (mirroring react-router's catch-all) — every other named route is also given an explicit path there (`game`, `about`, etc.) matching the old app's URLs, since a partial/missing `linking` config would otherwise leave unmatched URLs silently falling through to Home instead of showing the 404. Unlike the old web app there's no separate `/profile` route anymore — `SettingsScreen.tsx` (rendering the `Settings.tsx` component, formerly `ProfileScreen.tsx`/`MyProfile.tsx`) is reachable only via the `Settings` tab at `/settings`; a redundant standalone `Settings` stack route that duplicated the same screen (a dead web-router-compatibility leftover) was removed. `LoginScreen.tsx` (formerly `SigninScreen.tsx`) is registered under the `Login` route name (`/login`).

**Web layout** (`MainTabs.tsx`): on web, `Tab.Navigator`'s bottom tab bar is replaced with `WebTopNav.tsx` via the `tabBar` prop plus `tabBarPosition: "top"` in `screenOptions` (bottom-tabs renders whatever `tabBar` returns at the position given by `tabBarPosition` — without it, a custom `tabBar` still renders at the *bottom*). `WebTopNav` mirrors the original site's `HeaderCopy.tsx`: full-width bar containing a `max-w-4xl`-equivalent (896px, `WebCentered.tsx`) centered row — logo (`Logo.tsx`) + title + language flag, centered Home/Game/Progress/Settings/About links (active link bold+underlined, built dynamically off `state.routes` so tab renames propagate automatically), and a greeting (`AuthStatusIcon.tsx` + name) + Log In/Log Out button. Below `useWindowDimensions()`'s 768px breakpoint it collapses to a hamburger dropdown, same breakpoint as the original's Tailwind `md`. Each tab screen (and Login/Signup/Signout in `RootNavigator.tsx`) is individually wrapped in `WebCentered` rather than capping the whole navigator, since capping `Tab.Navigator` itself would also shrink `WebTopNav`'s full-width bar. `WebFooter.tsx` (web-only) reproduces the original's page footer.

Native's screen content is untouched by any of this — `isWeb` (`Platform.OS === "web"`) gates every branch — but native's per-screen header (`MainTabs.tsx`'s `screenOptions`) deliberately mirrors two of web's choices rather than diverging: `headerLeft: () => <HeaderLeft />` puts the logo + language flag in the same spot as `WebTopNav`'s brand cluster (the flag used to sit on the *right*, next to Log Out, via `HeaderRight.tsx` — moved for cross-platform consistency after it was flagged as confusing), and `headerTitle: () => null` hides the per-screen title text ("Game", "Settings", ...) the same way web's top nav has no "current page" label. `HeaderRight.tsx` keeps native's greeting + Log In/Log Out cluster (bottom tabs still show their own labels/icons as before — only the *header* title is hidden).

**Auth** (`src/context/AuthContext.tsx`): wraps Supabase auth (email/password, anonymous sign-in). Derives `authState` = `"visitor" | "guest" | "registered"` from session presence and `session.user.is_anonymous`. Anonymous ("guest") users get a real Supabase session, just flagged anonymous. `AuthStatusIcon.tsx` (used by both `WebTopNav.tsx` and `HeaderRight.tsx`, next to the greeting text) renders a small looping animation keyed off `authState` instead of a static glyph — 👋 (reuses `WavingHand.tsx`) for `visitor`, a gently nodding 👤 for `guest`, a twinkling ⭐ for `registered` — each its own `Animated.loop`. Both `logout()` and `deleteAccount()` pass `signOut({ scope: "local" })` **explicitly** — supabase-js defaults to `"global"`, which revokes every refresh token the user holds, so a plain "Log Out" in a browser would also sign them out on their phone. Don't drop the argument: the safety case for global is thin here (`clearStoredKeys()` already wipes the session and the in-progress round from the device), and in `deleteAccount()` a global sign-out is a guaranteed-to-fail round-trip since the `auth.users` row is already gone. The global counterpart is `logoutEverywhere()`, surfaced as `SessionsPanel.tsx` in Settings — both go through one `performSignOut(scope, timeoutMs)` helper. The timeout differs on purpose: 1s for a plain logout (which must never hang, and where being wrong costs nothing since the device is wiped locally anyway) versus 8s for "everywhere", where the answer decides whether the user can be *told* their other sessions are gone. `SessionsPanel` renders `null` for guests — a guest account has no credentials, so it can never have a second session to revoke. Registered accounts can be signed in on several devices at once; a guest session exists only on the device that created it.

`logout()` races `signOut()` against a 1s timeout and always clears local state/AsyncStorage `sb-*-auth-token` keys regardless of network outcome, so logout can't hang — the initial `checkAuthStatus()` call races `getSession()` against a 5s timeout for the same reason, and its `catch` path always sets `session` to `null` too, since `SessionGate.tsx` treats `session === undefined` as "still loading" and would otherwise spin forever for a logged-out visitor if `getSession()` hung or threw before `session` was ever set.

Profile rows (`player_profiles`) are fetched via `fetchOrCreateProfile()` in `AuthContext.tsx`: `getPlayerProfile()` (`src/supabase/players-repository.ts`) retries a few times on Postgres `PGRST116` ("no rows") to ride out the `on_auth_user_created` DB trigger's insert — a common race right after signup/anonymous sign-in — and if the row is still missing after that, `ensurePlayerProfile()` creates it client-side instead of leaving the session permanently profile-less (this also self-heals older sessions whose trigger insert failed outright, e.g. a guest created before `display_name` was NOT NULL-enforced). A separate `profileLoading` boolean (distinct from `loadingInitial`) lets consumers like `Settings.tsx` distinguish "still fetching the profile" from "fetched and it's genuinely missing/errored," so they show a retry affordance instead of an infinite spinner.

`signUpNewUser()` branches on `session.user.is_anonymous`: a signed-in guest is **upgraded in place** via `updateUser({ email, password })`, which keeps the same `auth.users.id` so every FK (`player_profiles`, `game_scores`, `duel_matches`) follows automatically. Calling `signUp()` for a guest instead would mint a *new* id and strand their scores on an orphaned account. Two things the upgrade path must do that a fresh signup gets for free: write `player_profiles` explicitly (`handle_new_user()` is an AFTER **INSERT** trigger, so it never fires on an update, and the chosen display name would stay `Guest52`), and treat "your own current display name" as available (`isOwnCurrentName` in `SignupScreen.tsx`, same guard `Settings.tsx` uses). The account stays `is_anonymous` until the confirmation email is clicked, so the result carries `upgraded: true` and the screen says "keep playing" rather than "go to sign in".

`login`/`signUpNewUser`/`loginAnonymously` all return an `errorCode` (Supabase auth-js's `error.code`, e.g. `invalid_credentials`, `email_not_confirmed`) alongside the raw `error` message; screens pass both through `translateAuthError()` (`src/utils/authErrors.ts`) to show a localized message for known codes, falling back to Supabase's (always-English) raw text for anything unmapped. `SignupScreen.tsx` also does its own client-side validation before calling `signUpNewUser` — email required + format-checked, password minimum 8 characters with a required confirm-password field — as a first line of defense ahead of whatever Supabase's own (dashboard-configured, not visible in code) password policy enforces server-side.

Forgot-password is a two-step flow: `requestPasswordReset(email)` (an inline expandable panel on `LoginScreen.tsx`, not a separate route) calls `supabase.auth.resetPasswordForEmail` with a dedicated `RESET_PASSWORD_REDIRECT_URL` (same web-origin/native-custom-scheme split as `AUTH_REDIRECT_URL`, but pointed at `/reset-password` instead of the app root) so the emailed link lands on `ResetPasswordScreen.tsx`; clicking it authenticates the browser with a recovery session via `detectSessionInUrl` (same mechanism as email confirmation), which is enough for `updatePassword(newPassword)` (`supabase.auth.updateUser`) to succeed without the old password. Like signup's email-confirm redirect, this isn't wired up on native yet (no custom URL scheme handling registered).

**A `redirectTo` that isn't in Supabase's allow-list is silently replaced by the project's Site URL**, not rejected — so a broken emailed link looks like the client built the wrong address when the setting is actually in Dashboard → Authentication → URL Configuration. Both values live there and both matter: **Site URL** must be `https://wordlune.appfinningar.se`, and **Redirect URLs** must contain `https://wordlune.appfinningar.se/**` — the double asterisk is what lets the `/reset-password` path match, since a bare origin entry does not. This bit on 2026-08-25: Site URL was still `https://wordse.appfinningar.se` from before the rename, a subdomain that no longer resolves, so every reset link dead-ended on `DNS_PROBE_FINISHED_NXDOMAIN` while the app-side code was correct throughout. Note the domain is `wordlune.appfinningar.se`, **not** `wordlune.se` — that one was bought and then cancelled under ångerrätt. The email templates (Authentication → Emails) interpolate `{{ .SiteURL }}`, so they follow Site URL automatically; the sender address is separate again, under Project Settings → Authentication → SMTP Settings (Resend, `noreply@appfinningar.se`).

Guest accounts are never deleted by the app itself — a "Play as Guest" login creates a permanent `auth.users` row (just flagged `is_anonymous = true`) with an auto-refreshing session, so it persists forever unless something explicitly cleans it up. `supabase-ops/migrations/20260818_cleanup_anonymous_users.sql` (applied, `pg_cron` enabled) schedules a daily job deleting anonymous accounts inactive 14+ days, cascading into `player_profiles`/`game_scores`/`duel_matches` — the latter's FKs had no `ON DELETE` behavior before that migration and would otherwise block deleting a guest who'd played a Duel.

Players (guest or registered) can self-delete their own account from Settings' "Danger Zone" (`Settings.tsx`, confirmed via `ConfirmationOverlay`). A regular client can't delete its own `auth.users` row directly (needs the service-role key), so `deleteAccount()` in `AuthContext.tsx` calls `deleteOwnAccount()` (`src/supabase/players-repository.ts`), which RPCs into `public.delete_own_account()` — a `security definer` Postgres function (`supabase-ops/migrations/20260818_delete_own_account.sql`, same pattern as `cleanup_anonymous_users()`) that deletes `auth.users` for `auth.uid()`. Cascades through the same FKs as the guest cleanup job above; nothing else needs touching since the only other tables that ever referenced `auth.users(id)` directly (`matches`, `boards`) are unused dead code and `player_settings` is dead too (settings actually live in `player_profiles.metadata`, see `updatePlayerSettings()`). After a successful delete, `deleteAccount()` clears local session state the same way `logout()` does.

**Game engine** (`src/hooks/useGame.ts`): owns the core Wordle state machine — persisted to AsyncStorage (`wordlune:game:v1`) for practice mode only; duel/challenge modes always start from an explicit secret and skip persistence/restore. `evaluateGuess` normalizes hyphen/dash variants and whitespace so multi-word or hyphenated secrets (e.g. category words) evaluate sensibly. Mode is one of `"practice" | "competitive" | "duel"`, driven by `gameModeProp` plus `overrideSecret`. `addLetter` also implicitly starts a round (`idle`→`playing`) if a player types before pressing ▶ Play — that transition stamps `startTime` too, not just the explicit `startPlaying()` path, since `PracticeResultOverlay`'s elapsed-time display (`durationSeconds`) needs both `startTime` and `endTime` set and silently falls back to showing 0 otherwise.

Composed hooks layered on top of `useGame`, all driven from `GameScreen`:
- `useWordPool` — fetches/filters the candidate word list from Supabase (`words-repository.ts`) based on mode/category/subcategory/length filters; also picks the initial secret for practice mode. **Duel** validates guesses against every 5-letter word in the active language (`listFiveLetterWords`), while its secret is drawn separately in `DuelLobby` (`getRandomFiveLetterWord`) — deliberately the same source, so validation can be on without rejecting most of the language. Until 2026-08-25 both were scoped to the Hydrocarbons category, and the pool lookup searched for a *subcategory* of that name which does not exist, so it always returned `[]` — which made `submitGuess` skip its `candidatePool.length > 0` guard and silently accept any five-letter string in Duel. `listHydrocarbonFiveLetterWords`, `getFiveLetterHydrocarbon` and `getAllHydrocarbonSubcategories` were removed with it; nothing in the app treats Hydrocarbons as special any more.
- `useDuelMode` — realtime 1v1 duel logic over a Supabase Realtime channel (`game:<matchId>`), broadcasting `guess`/`duel_status`/`game_control` events and using presence sync to detect opponent disconnects (auto-awards victory if the opponent leaves mid-duel). Scoring: 5 pts per correct letter, 2 pts per present letter, summed client-side per player and reconciled via broadcast. **Every path that finishes a match goes through the hook's `recordVictory`, never `claimVictory` directly** — including GameScreen's own win and surrender handlers, which is why the hook exports it. `duel_matches` gained `player1_score`/`player2_score` in `20260827`; before that the final scores existed only in this hook's state and were lost when the match ended, so duel history could show who won but not by how much. Both scores are mirrored into a ref because two of the call sites live inside the channel's `subscribe` callbacks, which capture their closure once — reading the state there yields 0/0 forever, the same trap `duelElapsedRef` already works around. **Duels end on a clock now** (`20260828_duel_timeouts.sql`): 2 minutes without a submitted guess forfeits you, *but only while your opponent is still able to act and is not also idle* — and 8 minutes with neither player acting is decided on proximity. Those two interlock deliberately: an 8-minute cap that resets on activity can never fire on its own, since the 2-minute rule resets on the same event and is shorter, so restricting the forfeit to the one-sided case is what leaves the both-idle case for the longer clock and makes both numbers reachable. **Activity means an *accepted* guess and nothing else** — a word that was in the candidate pool and so consumed one of the six attempts. Not typing, not presence, not having the tab open, and specifically not a word `submitGuess` rejected: a rejected word costs no attempt, so if it reset the clock the way to stall forever would be to hammer Enter on gibberish. `useDuelMode` enforces this with `reportedGuessCountRef` rather than leaning on `evaluations`' reference identity — that identity happens to change only on an accepted guess today, but a refactor that copied the array on the way out of `useGame` would make the duel clocks unexpirable, and nothing would notice until a duel refused to end. **A duel where neither player ever guessed is voided, not decided** (`finish_reason = 'abandoned'`, `winner_id NULL`): "never a draw" was about deciding contests, not about inventing a winner where there was no contest, and both `duel_leaderboard` and `my_duel_history` require a winner so a voided row simply doesn't appear. Without that carve-out the proximity ladder falls straight through — greens, yellows, guesses and activity all tied at zero — and awards player1 on the final deterministic fallback, which on first apply would have turned 41 abandoned lobbies into 41 free wins. **Proximity is best-guess greens, then best-guess yellows, then fewer guesses, then most recent activity, then player1** — never the score, which sums every letter of every guess and so measures how *much* you have guessed rather than how close you are (five sloppy guesses at two yellows score the same 20 as one guess with four greens; under a timeout rule that becomes a stalling strategy). The verdict is always `resolve_duel()`'s, never a client's: it row-locks and no-ops once the duel is finished, so both clients calling it cannot disagree — which also fixes the both-lost path, where only the client that believed it led called `claimVictory`, so an exact tie left the match at `status='playing'` forever behind a "Draw!" dialog. `sweep_stale_duels()` runs every 5 minutes via `pg_cron` for matches both players abandoned, since a client timer cannot fire when no client is running. `DuelDashboardHeader` shows **all three** clocks at once — match, you, opponent — because any of them can end the duel and hiding one until it matters means being surprised by it; the two player clocks grey out together when both players are past the limit, since neither can fire then. Their warning/alarm thresholds are proportional (a quarter and a tenth of each clock) so the 8-minute and 2-minute timers escalate at the same relative moment.

`BoardGrid` exports `useBoardTileSize()` so `OpponentBoard` can size itself from your board (`OPPONENT_SCALE = 0.7`) instead of the fixed 22px it used to pin. The fixed size meant the two boards drifted further apart the more room the viewport had — yours grows to 38px on a desktop while the opponent's stayed put.

The hook owns `suddenDeathEndTime`/`setSuddenDeathEndTime` and the auto-forfeit timer off it, but never *sets* it itself — `GameScreen.tsx` must call `setSuddenDeathEndTime(Date.now() + 60000)` when `opponentLost` fires (mirroring the web app's `Game.tsx`), or the whole mechanic silently never triggers despite the hook's internals working fine.
- `useChallengeMode` — multi-word "challenge" runs backed by `challenge_attempts`/`challenge_results` tables; tracks progress index across a fixed word list and only persists a summary row at the end (per-word scores aren't saved individually in competitive/challenge mode). Challenges are a **rotating weekly schedule** generated ~six months ahead by `supabase-ops/scripts/generate_challenge.mjs` — a `start_date`/`end_date` window per row, with `challenge_menu_stats` returning only the active week and `competitive_challenges`' RLS hiding anything that hasn't started (a queued challenge is an answer key; the table was `SELECT USING (true)` until `20260826_challenge_rotation_reset.sql`). Category names are resolved by that view from `subcategories` at read time in all three languages; the `description` column is the old frozen-at-generation snapshot and is left NULL — it is what let two retired subcategories keep advertising themselves for months. `is_five_chars` only started reaching the client with that same migration: `20260131_add_is_five_restricted.sql` added it to the table and never rebuilt the view, so the 5x5 badge never rendered and `setOverrideFive(true)` never ran.

A finished challenge is **replayable while its week is open** (`restartChallengeAttempt()` → `restart_challenge_attempt()` RPC, `20260827`), which also undoes a misclicked forfeit. It resets the existing `challenge_attempts` row rather than inserting a second one, so `UNIQUE(player_id, challenge_id)` and everything reading it stay as they were. **Only the first completed run ranks**: `leaderboard_entries` is `DISTINCT ON (player_id, challenge_id) … ORDER BY completed_at ASC`, because on a replay the player already knows all five words — ranking the best run would rank willingness to replay and nothing else. Previous `challenge_results` rows survive, so a player's own history shows every attempt.

**Progress** (`ProgressScreen.tsx`) has one tab per game mode, not per data source: Practice / Competitive / Duel, matching `GameModeToggle`'s order and icons. Competitive and Duel each render `progress/TwoColumn.tsx` — the player's private history beside the public list it feeds, side by side above 768px (the same `md` breakpoint `WebTopNav` collapses at) and stacked below it, private first. Practice deliberately has no second column: a practice round is played against a word list the player chose, so there is nothing to rank it against; the screen says so rather than leaving an empty column. Duel has no per-row publish toggle either, and can't: a duel is two people's row, so one of them cannot decide to publish it — what reaches `duel_leaderboard` is the win/loss tally, gated on the profile-level `is_public`. That view **ranks on `diff` (wins − losses), not on wins** — ranking wins alone ranks whoever has played most, putting a 20–15 record above a 9–0 one, which is the opposite of what a leaderboard says. Ties break on wins, so at equal difference the longer record places higher. `DuelLeaderboard.tsx` gives the diff the visual weight and the raw record the small print, because a list sorted by one number while displaying another looks arbitrarily ordered. The panels (`JustPlayingScores`/`CompetitiveScores`/`LeaderboardScores`) carry no card headers of their own any more; `TwoColumn` supplies the heading and the one-line privacy statement.

**Scoring** (`src/utils/scoring.ts`) is one module because it used to be three copies of `Math.max(10, 100 - (guesses - 1) * 10)` — in `GameScreen`'s `handleSaveScore`, in `useChallengeMode`, and implicitly in each result overlay — which is precisely why the rules could never be shown to a player: there was no single thing to show. A word is worth `guessPoints + timeBonus`, max 150: 100 minus 10 per guess after the first (100…50 over six guesses), plus up to 50 for speed. The time allowance is **per letter** (10 s × word length) rather than a flat budget — a flat one hands the bonus to whoever plays short words and denies it to everyone else, i.e. punishes the harder round. Past the allowance the bonus decays 1 point per 2 seconds. A lost, skipped or forfeited word scores 0. Duel is unchanged (5 per correct letter, 2 per present) since time is already its mechanic, but the constants live here too. `ScoreBreakdown.tsx` renders the arithmetic from the same module in the result overlays, in a modal on Progress, and as a section on About, so the explanation cannot drift from what was computed. `explainStoredScore()` exists because rows written before the time bonus cap out at 100: it flags them rather than printing arithmetic that doesn't add up.

**The candidate pool doubles as the dictionary.** `useGame.ts`'s `submitGuess` rejects any guess not present in `candidatePool`, so a category is both the set of possible answers *and* the set of accepted guesses. A thin category therefore doesn't merely offer fewer answers — it makes the game feel broken, because ordinary words are refused mid-round. That's the reason the hydrocarbons set was expanded from 179 to 357 rows (see `supabase-ops/README.md`); it is *not* a fix, since even 357 words means most real five-letter words are still refused. Decoupling the two — a per-language guess dictionary, with the category only choosing the answer — is the actual fix and hasn't been done.

**Supabase layer** (`src/supabase/*-repository.ts`): thin query wrappers, no ORM. Key tables: `player_profiles`, `game_scores`, `challenge_attempts`/`challenge_results`/`competitive_challenges`, `duel_matches`, `words`/`categories`/`subcategories`/`words_subcategories`. Words are stored with per-language columns (`word_en`, `word_se`/`word_sv` — note the inconsistent `se`/`sv` suffix across tables, handled ad hoc per query). Leaderboards read from DB views (`leaderboard_entries`, `duel_leaderboard`, `player_history_view`, `challenge_menu_stats`) rather than raw tables so visibility/aggregation rules live in Postgres, not the client. `answer_eligible_words` follows the same pattern for content rather than privacy: **being a valid guess and being allowed to be the answer are different things.** `subcategories.is_answer_eligible` is false for proper-noun lists ("Cities in Sweden", "Villages on Öland"), so they can't be drawn as a secret — a French duel handing someone "Dorby" is unwinnable in practice — while their words stay valid guesses everywhere and stay playable in practice mode, where the player picks the category deliberately. A word linked to *any* eligible subcategory stays eligible. See `20260825_answer_eligible_subcategories.sql`; the flag survives reseeding because the master seed's `ON CONFLICT DO UPDATE` only touches the name columns.

**RLS model** (`supabase-ops/migrations/20260821_gdpr_privacy_helpers.sql` + `20260822_gdpr_rls_lockdown.sql`): every personal-data table is **own-row-only** (`auth.uid() = player_id`). Before those migrations, `player_profiles`, `game_scores`, `challenge_results` and `duel_matches` all carried `SELECT USING (true)`, meaning the whole tables were readable with the anon key that ships in the web bundle — the `is_public` opt-in existed only in the views, never in RLS, so it protected nothing against a direct PostgREST query. Anything that legitimately needs to show *other* players now goes through an owner-rights view or a `security definer` RPC that applies its own gate: `display_name_available()`/`suggest_display_name()` (signup name checks), `duel_lobby` (open invitations — deliberately omits `secret_word`, which non-participants could previously read straight off `duel_matches`), `match_player_names()` (participants only), and the three leaderboard views (each gated on `is_public`). `player_history_view` is `security_invoker = true` *and* filters on `auth.uid()`; the leaderboard views are pinned `security_invoker = false` explicitly so a future default change can't silently empty or expose them. When adding a query that reads another player's row, add a gated RPC/view — don't loosen the table policy.

**`challenge_results` was missed too, and worse.** It is listed among the own-row tables above, and it does carry `USING (auth.uid() = player_id)` — but a second policy, `"Authenticated can read challenge_results" FOR SELECT TO authenticated USING (true)`, sat beside it until `20260827_replay_and_duel_history.sql`. Policies are OR'ed, so the own-row one was decorative and any signed-in account — a guest created by pressing "Play as Guest" included — could read every player's challenge scores off PostgREST regardless of `is_public`. The lesson from `20260824` generalises: after adding an own-row policy, count the *permissive* ones that remain, don't check that yours exists. `supabase-ops/scripts/migration_state.sql` does exactly that, as a standing check.

`competitive_challenges` was missed by that lockdown and kept `SELECT USING (true)` until `20260826_challenge_rotation_reset.sql`. It holds no personal data, so the leak was a *spoiler* rather than a privacy one — but `word_ids` is the answer list, and the schedule is now written months in advance, so the same policy would have published half a year of answers to anyone holding the anon key from the web bundle. It is now gated on `start_date <= now()`; expired challenges stay readable on purpose, since `getMyChallengeResults()` joins their name to label a player's own history. Note what this does *not* do: the currently-running challenge's words are readable, because they have to reach the client to be playable. Policies are OR'ed, so the migration drops existing SELECT policies by enumerating `pg_policies` rather than by name — the same lesson as `20260824_gdpr_rls_lockdown_fix.sql`.

The old generic `board_events`/`board_state` pub/sub layer (`src/shared/useBoardRealtime.ts` plus four helpers in `words-repository.ts`) was **removed** — it had zero consumers anywhere in `src/`, and its `user_id` column was personal data that no deletion path could reach. `matches`, `boards` and `player_settings` were dropped in the same migration for the same reason. Duel realtime is unaffected: it lives in `useDuelMode`'s own channel.

**i18n** (`src/i18n/i18n.ts`): `en`/`sv`/`fr` resources from `src/locales/*/translation.json` — all three files must share the exact same key set (verify with a `t("...")` grep-vs-JSON-diff sweep across `src/`; the project has been bitten before by locale drift). Language is never auto-detected from device locale — it defaults to English and only restores a previously *user-selected* language cached in AsyncStorage (`wordlune:lang`), mirroring the web app's detector config. `WebTopNav.tsx`/`HeaderLeft.tsx` (native) expose language switching as a single flag icon next to the logo that *cycles* en→sv→fr→en (`src/utils/languageCycle.ts`'s `LANGUAGE_CYCLE`/`flagFor`/`nextLanguage`) rather than a dropdown — deliberately minimal for 3 languages, revisit if a 4th is added. French is **accent-sensitive** by design (like Swedish ÅÄÖ, unlike some other language Wordle clones) — "cafe" does not match secret "café"; this needed no comparison-logic changes since `evaluateGuess`/`normalizeForCompare` (`src/hooks/useGame.ts`, `src/utils/wordUtils.ts`) already did plain exact-character matching.

The on-screen keyboard (`Keyboard.tsx`'s `LAYOUTS`) uses real AZERTY rows for French (`AZERTYUIOP`/`QSDFGHJKLM`/`WXCVBNÄÖÅ`) plus a 4th row of the 10 real French accented letters (`ÉÈÊÀÂÇÎÔÙÛ`); the physical-keyboard handler in `GameScreen.tsx` (`LETTER_PATTERNS.fr`) accepts the same set plus Å (Å isn't native French but is needed for the Swedish-place-name loanwords below — easy to forget since it's not visually grouped with Ä/Ö). Ä/Ö/Å (also not native French) are tacked onto the end of the `WXCVBN` row rather than the already-full accent row. Delete (`⌫`) lives on the Enter row for *every* language now — to the right of Enter, in a `flex`-shared zone with whatever else is on that side — rather than at the end of the last letter row, so it has one consistent, predictable spot regardless of how many letter rows a language has. French additionally moves space/hyphen to the Enter row's *left* zone (`SPACE_HYPHEN_ON_ENTER_ROW`), since its accent row has no room left for them. The Enter key itself is a fixed 50%-width, always-centered `Pressable` flanked by two equal-`flex` zones (so it stays centered whether one zone is empty or both hold keys) — its side-key children (`sideKey` style) are deliberately never combined with the letter-key style (`key`) in one `style={[...]}` array, since react-native-web can flatten conflicting `flex`/`width` values from merged style objects unpredictably and collapse a button to near-zero width.

Word/category/subcategory content is per-language via `word_en`/`word_sv`/`word_fr` and `name_en`/`name_sv`/`name_fr` columns (`words`/`categories`/`subcategories` tables) — `src/supabase/langColumns.ts`'s `wordColumn()`/`nameColumn()` resolve a language code to the right column name (also fixed a latent bug where some queries used a nonexistent `word_se` column instead of `word_sv`). `supabase-ops/migrations/20260818_add_french_language.sql` added the `_fr` columns and populated them for every existing word/category/subcategory — brand-name categories (car/bicycle/motorcycle) got `word_fr = word_en` (untranslatable proper nouns), Swedish place-name categories got `word_fr = word_sv` (keeps correct native diacritics), everything else (countries/capitals/hydrocarbons common nouns/ship types) got real French translations. The seed CSVs (`supabase-ops/migrations/seeds/**/*.csv`) mirror the same translations in new `_fr` columns for future-reseeding value, though the live DB was populated directly by the migration, not by re-running the seed pipeline. `supabase-ops/scripts/generate_challenge.mjs` requires a word to exist in all three languages (not just en/sv) before selecting it for a daily challenge.

**Every word must be typeable in its own language, and letters are only part of that.** A word column may contain only what that language's keyboard can produce: `Keyboard.tsx`'s `LAYOUTS` plus space and hyphen, matched by `GameScreen.tsx`'s `LETTER_PATTERNS`. Anything else — an apostrophe, an ampersand, a parenthesis, a diacritic the layout lacks — makes that round unwinnable, because there is no key to press. So `word_en` must be ASCII-transliterated even where `word_fr` deliberately keeps native diacritics (the Swedish place-name categories above): `Färjestaden` as `word_en` is unsolvable, `Farjestaden` is not.

Two migrations cover this. `20260820_fix_english_diacritics_oland_skanor.sql` fixed 31 rows in "Villages on Öland" and one in `cities-sweden.csv`, but was scoped to those two files. `20260825_fix_unspellable_words.sql` is the full audit across every category and language, and found that diacritics were only one of four causes — the others were apostrophes (`NUKU'ALOFA`, `ST GEORGE'S`), an ampersand (`RIESE & MÜLLER`), and parentheses that were disambiguation metadata leaking into the answer (`BLASINGE (BORGHOLM)`, `ROYAL ENFIELD (APACHE)`). Where correct spelling and typeability conflict (`MOÇAMBIQUE`, `MÜSLI` in Swedish), typeability wins: a word nobody can enter is worth nothing however correctly it is spelled.

A third cause surfaced on 2026-08-25 that the `20260825_fix_unspellable_words.sql` audit missed: **`LETTER_PATTERNS` is not the binding constraint — `LAYOUTS` is.** The physical-keyboard regex in `GameScreen.tsx` deliberately accepts more than the on-screen keyboard can produce (`Ë`, `Ï`, `Ü`, `Æ`, `Œ` for French; `É` reaches the Swedish regex through `A-Za-z`'s neighbours too), so auditing against it passes words no player can actually type on a phone. French offers only `ÉÈÊÀÂÇÎÔÙÛ` plus `ÄÖÅ`; Swedish only `ÅÄÖ`. That let `THAÏLANDE`, `HAÏTI`, `ISRAËL`, `CITROËN`, `MAÏS` and eight more through as unwinnable rounds, fixed in `20260825_fix_french_dieresis.sql`. Audit against the `LAYOUTS` character sets, not the regex.

Adding content? Run the check at the foot of `20260825_fix_french_dieresis.sql` (the `LAYOUTS`-derived one — the older check in `supabase-ops/README.md` is the looser regex version) — it returns every row that cannot be typed, and should return none. Do **not** rely on prose in either file for whether a migration has been applied; that claim was wrong three times in a row before this was written. There is no migration-tracking table yet, so the database is the only authority — query it. `supabase-ops/scripts/migration_state.sql` is that query for the content migrations: read-only, safe against production, and it infers each migration's state from the data rather than from a record of what someone believes they ran (so it stays correct after a restore, too).

**The Supabase SQL editor keeps one session but commits every statement separately.** Both halves matter, and getting either wrong has already cost a half-applied migration. Because the session is shared, an ordinary `CREATE TEMP TABLE` survives into the following statements — which is why `20260819_master_seed_with_french.sql`'s `tmp_norm`/`tmp_src` work there. Because each statement commits on its own, a temp table declared `ON COMMIT DROP` is gone before the next statement runs, and `20260825_remove_bicycle_brands_and_at_sea.sql` died on `relation "doomed_subcats" does not exist` — *after* its two `DELETE`s had already committed, leaving the migration half applied with its assertions unrun. The same autocommit means an explicit `BEGIN`/`COMMIT` around a migration buys no atomicity at all; it only looks like it does, and the trailing `COMMIT` warns `there is no transaction in progress`.

So a migration meant for the SQL editor should be **one statement**: a single `DO $$ ... $$` block, holding its working set in local variables (`UUID[]` plus `= ANY(...)` replaces the temp table) and using `GET DIAGNOSTICS ... = ROW_COUNT` for the counts the assertions check. A DO block is atomic on its own, so it cannot half-apply. `psql` hides all of this — it holds one session for a whole file and honours the file's own transaction — so rehearsing with `docker exec ... psql -f` proves nothing about the editor. Rehearse by running each top-level statement on a separate connection; anything that survives that is safe either way.

**Google Play**: not published, and deliberately not started — see `GOOGLE-PLAY.md` for the full pre-publication checklist (what's already done, the release-signing blocker, the Data safety answers, and the 12-testers-for-14-days timeline trap on personal developer accounts). Android-side GDPR/permission work is already landed; don't redo it.

**Hints are always on, in all three modes**, and both toggles that used to control them (each off by default) are gone — the lobby's `showHint` and `LetterSlider`'s `showHintToggle`, along with the now-orphaned `enable_hints` / `no_hint` / `show_hint` keys. The game is meant to reward general knowledge; without the category the answer is one of a couple of hundred unrelated words and the round is guesswork instead. Practice keeps a second reason: selecting no categories makes the pool everything, and the hint is then the only thing that says what the word is even about. Competitive had no hint at all before — its categories were only ever visible in the menu, i.e. only before the clock started, which is the wrong way round.

**But a hint only ever shows while the round is running** (`status === "playing"`, gated once in `GameScreen` as `showHint`, `paused` excluded). That is a rule about the clock, not about tidiness: time is part of the score now, so a hint visible at `idle` hands the player free thinking time — study the category, plan an opening word, then start a timer that has already been beaten. The same reasoning removed the theme from the challenge *name* (`20260829_neutral_challenge_names.sql`) and the category list from `ChallengeSelector`: the menu is seen before the clock starts, so anything it reveals can be prepared against. Competitive gained a per-word hint in the challenge banner in exchange, which it never had before. `challenge_menu_stats` still resolves `subcategory_names_*` and nothing reads them — they are kept as the honest source if categories are ever shown *after* completion, where revealing them costs nothing. It was never a fairness problem — `is_hint_enabled` lives on the match, so both players always shared it and every duel was a fair contest in itself; the only real asymmetry was that the creator chose the joiner's difficulty. It was a playability problem. Since `20260825` the secret is drawn from the whole language's answer-eligible five-letter words — **204 in English, 180 in Swedish, 160 in French** — spanning animals, groceries, countries, car brands and body parts with nothing tying them together, and the subcategory hint narrows that to typically 10–36 candidates. Without it there is no anchor at all. The column and `createMatch`'s parameter stay for history; nothing passes false any more, and `DuelChallengeCard`'s 💡 badge went with the toggle since it would now be on every card.

`DuelDashboardHeader`'s hint shows the secret's own subcategory names, the same hint the practice screen gives (`LetterSlider`'s `hintNames`). It used to render a fixed row of every Hydrocarbons subcategory with the matching ones highlighted — a decoy-and-reveal design that only worked while every duel secret came from that one category.

**GDPR surfaces**: `PrivacyPolicyScreen.tsx` (`/privacy`) and `DeleteAccountScreen.tsx` (`/delete-account`) are root-stack routes, both deliberately **outside** `SessionGate` — a visitor must be able to read the policy before signing up, and both URLs are registered with Google Play (Play requires a *web* URL for account deletion even though the app offers it in-app). `DeleteAccountPanel.tsx` is the single implementation of the delete flow, rendered by both that screen and Settings' Danger Zone. Policy text lives in ~78 flat `privacy_policy_*` / `delete_account_*` i18n keys at paragraph granularity (not one key per section — that makes translation review impossible), and `PRIVACY_POLICY_VERSION` in `src/constants/privacy.ts` doubles as the policy's "last updated" date so the stamped version and the displayed date can't drift. Note `privacy_status` is an *old* key meaning leaderboard visibility, not a GDPR statement — its display text was renamed accordingly.

**Avatars** (`src/components/Avatar.tsx`): generated locally with `react-native-svg`, deterministically from a seed — never fetched. `avatar_url` holds a `wordlune:avatar:<seed>` token (`localAvatarUrl()`), and a **null** `avatar_url` is normal: `Avatar` then derives the seed from the display name. This replaced `api.dicebear.com` URLs, which sent another player's display name *and the viewer's* IP/User-Agent to a third party on every profile, leaderboard and duel-card render, for a decorative image. `Avatar` still renders a leftover `http(s)` URL as a remote `Image` so native clients on an older bundle don't break; that branch can go once they can't write one (`20260823_drop_dicebear_avatars.sql` nulls the existing rows). Don't reintroduce a remote avatar service without adding it to the CSP, the policy's recipient list, and the Play Data safety declaration.

**Data export** (`exportMyData()` in `players-repository.ts` + `src/utils/exportDownload.ts`): the Art. 15/20 request, self-served from Settings → Data & Privacy. Six parallel own-row queries plus the `wordlune:*` device keys, delivered as JSON. Web and native need genuinely different delivery — react-native-web's `Share.share()` delegates to `navigator.share` and *rejects* when unavailable, so the Blob/`<a download>` path is required, not a nicety; native writes to `Paths.cache` and opens the share sheet via `expo-sharing`. The session token is deliberately excluded from the export: it's a live credential, not user data.

**Local storage** (`src/utils/localStorageKeys.ts`): every `wordlune:*` AsyncStorage key is declared here rather than as a module-local const in its consumer, so `clearStoredKeys()` can wipe them on logout/deletion without a second hardcoded copy of each string. Scope differs per path on purpose: **logout** clears the Supabase session + `wordlune:game:v1` (it holds the secret word, which matters on a shared computer) but keeps theme/language/reduceMotion as device preferences; **account deletion** clears all of it.

**Theming** (`src/theme/`): light/dark palette context (not system-linked), always initializes to `"dark"` on boot regardless of persisted value, matching the web app's behavior. Screens consume `colors` from `useTheme()` and apply them manually in `StyleSheet` — there's no CSS-class-based theming.

The palette is **shared with the `appfinningar-se` repo** (the parent portfolio site this app is a subdomain and a project card of). `src/theme/palettes.ts`'s dark values are lifted from that repo's `src/styles/global.css` custom properties; when one changes, the other should follow. Three deliberate divergences:

- **The board and keyboard tile colours stay Wordle's** green/yellow/grey (`BoardGrid.tsx`, `Keyboard.tsx`, and `OpponentBoard.tsx`, which was aligned to the same three). They're the rules of the game, not decoration — restyling them to match the brand costs comprehension and buys nothing. They're the only hardcoded hexes left in `src/` besides `Avatar.tsx`'s deliberately-rainbow seed palette and `Card.tsx`'s shadows.
- **Light mode is flat.** appfinningar.se is dark-only on purpose (translucent cards need something dark behind the glass), so light mode here keeps the hues and drops the transparency rather than rendering the glass as grey plates.
- **`accent`/`success`/`danger`/`warning` differ per theme.** `#16a34a` and `#dc2626` are legible on white and nearly vanish on `#0d1533`, so dark mode uses lifted variants. Before this, ~250 hardcoded hexes across ~40 files meant a lot of light-mode-only colour (`#eef2ff` chips, `#ffffff` input fills, `#fef2f2` danger boxes) was simply unreadable in the default dark theme.

`colors.surface` is **translucent in dark mode**. Anything content can pass behind — a dropdown, a modal, a sticky bar, a tooltip, a cover overlay — must use `colors.surfaceSolid` instead, or it reads as a rendering fault rather than as depth. `surfaceSunken` is for inputs and wells.

**The gradient background is painted once, behind everything, and every navigator scene must stay transparent to show it.** `App.tsx` sets React Navigation's `colors.background` to `"transparent"` and both navigators pass a transparent `contentStyle`/`sceneStyle`; the root `View` in `AppShell` only takes a base colour on native. Add a screen that sets its own opaque background and it will cover the gradient on that route only — which is exactly how it looks when someone reintroduces `style={{ backgroundColor: colors.background }}` on a `PageScrollView`.

That transparency has one consequence worth knowing before touching `MainTabs.tsx`: **on web, bottom-tabs does not hide the tabs you aren't looking at.** `react-native-screens` sets `ENABLE_SCREENS = isNativePlatformSupported` (ios/android/windows), so on web `screensEnabled()` is false, `MaybeScreen` degrades to a plain `View`, and `BottomTabView` separates the scenes with nothing but `zIndex: -1` — every tab you have visited stays mounted *and painted*, stacked behind the focused one. That was harmless only for as long as each scene painted an opaque `theme.colors.background` on top of the ones below. With transparent scenes it shows up as a stale screen lingering behind the current tab (most visibly `SessionGate`'s sign-in card, which looks like an overlay that won't close). `MainTabs.tsx`'s `TabScene` wrapper is the fix: `useIsFocused()` plus `display: none`, web-only, children left mounted so in-progress state survives a tab switch. Every `Tab.Screen` component must go through it. The root stack needs no equivalent — `NativeStackView` sets an explicit per-screen `display` on web.

Web and native draw that background differently, and neither is a fallback for the other:

- **Web** (`src/theme/webTheme.ts`): real CSS injected into a `<style id="wordlune-theme">` and applied to `<body>`. Three things force this — several `radial-gradient`s on one element, `background-attachment: fixed` (the glow must stay put while content scrolls, which is what gives the translucent cards something moving to read against), and `backdrop-filter`. None has a React Native expression. The blur reaches components through `glassProps`, a `dataSet` that react-native-web renders as `data-wl-glass`; `PageTitle`'s gradient-clipped heading fill works the same way via `data-wl-gradient-text`, and needs `!important` because RNW writes `color` as an inline style. `public/index.html` also carries a `<style id="wordlune-boot">` with just the flat base colour, so the first paint isn't white while the bundle loads — keep it and the `theme-color` meta in step with `palettes.ts`.
- **Native** (`src/theme/AppBackground.tsx`): the same gradient drawn with **react-native-svg**, which supports `RadialGradient` and is already a dependency (`Avatar`/`Logo`/`DuelIcon`). `expo-linear-gradient` was deliberately *not* added: it has no radial mode, and adding a native module to this bare-workflow repo would mean rebuilding the committed `android/` and `ios/` trees for an effect SVG already covers. `Button`'s gradient fill and `SectionHeading`'s rule use the same trick. Blur is skipped on native on purpose — the background there is a static gradient, so blurring it returns the gradient at real cost on Android.

**Every react-native-web `View` is its own stacking context.** RNW emits `position: relative; z-index: 0` on the base View style, and a positioned element with a numeric z-index starts a new stacking context — so a `zIndex` set on a floating child (a tooltip, a dropdown, a popover) is *trapped inside its own parent* and can never lift it past that parent's siblings. Raising the number does nothing; the fix is to raise `zIndex` on every ancestor between the floating element and the nearest common parent with whatever it must cover. `GameModeToggle`'s hover tooltip and `CategorySelector`'s `container`/`headerRow` carry the matching values and a comment saying so — change one and the tooltip silently slides back under the row below it. The same trap explains why anything floating out of a `Card` gets cut: `Card` sets `overflow: "hidden"`, so a bubble needs to open into the card's interior rather than out of its edge.

**Shared UI primitives** live in `src/components/ui/`: `Card` (the glass surface — its 1px top hairline is a real `View`, since RN has no `inset` box-shadow), `Button` (`primary` gradient / `ghost` / `danger` / `subtle` — never two filled buttons side by side), and `Heading` (`PageTitle`, `SectionHeading`). Prefer these over hand-rolling another bordered `View` with `colors.surface`.

**Board tiles on web** (`src/components/BoardGrid.tsx`): tile size is fixed per word length on native (phone-tuned table), but on web it grows to fill available space via `useWindowDimensions()` — bounded by both a width fit (against the 896px `WebCentered` column) and a height budget (`windowHeight * 0.32`, since the board sits in a `ScrollView` alongside the header/controls/keyboard/footer). The overall cap is deliberately modest (38px, not width-fit's actual max) — raising it reintroduces vertical scrolling on shorter desktop viewports because the height budget was tuned against that cap, not derived independently. `Keyboard.tsx` intentionally keeps its original fixed key size on web (not scaled to match) per explicit user preference.

**Mode toggle / header-row pills** (`src/components/GameModeToggle.tsx`, sitting in `CategorySelector`'s `headerRow`): both the Practice/Competitive/Duel toggle buttons and `CategorySelector`'s "Select Categories" expand button use an explicit fixed `height: 40` (not padding-derived height) so they line up pixel-for-pixel on the shared row — emoji glyphs (☕🏆⚔️) render with inconsistent line-box metrics across browsers/fonts, so matching heights via padding+line-height alone doesn't reliably hold across environments. `GameModeToggle` renders all three modes as icon-only 40×40 squares — no text label even for the active mode; the active one is signaled by a `colors.accent` fill instead, and `accessibilityLabel` carries the full name for screen readers. On web, `onHoverIn`/`onHoverOut` show a small custom tooltip bubble with the mode name — react-native-web doesn't forward a `title` prop through `Pressable` to the DOM, so a native browser tooltip isn't an option here; native has no hover concept so the tooltip simply never renders there (no `Platform.OS` check needed).

**Letter-range filter** (`src/components/LetterSlider.tsx`, used from `GameScreen.tsx`): renders as `[−] min [+] ≤ ABC ≤ [−] max [+] (count)` on one row — `+`/`−` stepper buttons, not the native slider it originally was (`@react-native-community/slider` was removed from `package.json` entirely; `LetterSlider` was its only user). Buttons are visually compact (32px) but use `hitSlop={8}` to still meet Material Design's 48dp minimum touch target without inflating the row's height. The displayed min is `minValue + 1` with `≤` on both sides, even though the underlying filter is exclusive (`word.length > minValue`) — mathematically identical, but "1 ≤" reads better than "0 <" for a count that can never be 0.

`DEFAULT_MAX_LETTERS = 8` (`GameScreen.tsx`) is a genuinely active filter, not a "no filter yet" sentinel like it briefly was mid-refactor — `filterMax` is always `maxLetters`, never `undefined`. It's capped at `ABSOLUTE_MAX_LETTERS = 12`: past that, `BoardGrid.tsx`'s native tile size table shrinks to a near-illegible 14px and — since that row has no horizontal scroll fallback — the board can overflow narrow phone screens outright. `ControlDashboard.tsx`'s Play button is disabled (with a `no_words_for_filter` hint text) whenever the current filter/category selection yields zero words, rather than letting a player start a round they can never win.
